구조를 이해하는 개발

화면 하나를 만드는 데서 끝나지 않고, 요청이 서버를 거쳐 데이터베이스에 저장되고 다시 사용자에게 전달되는 전체 흐름을 이해하려고 합니다. 그래서 기능 구현뿐 아니라 구조 설계에도 관심이 많습니다.

고치기 전에 먼저 재봅니다

부하테스트에서 병목을 커넥션풀로 지목했지만, 고치기 전에 확인했더니 제 진단이 틀렸습니다. 측정 프로토콜을 세워 다시 재고 진짜 병목을 특정했습니다. 개선안도 기준에 미달하면 근거를 남기고 기각합니다.

무엇을 잃는지 알고 결정합니다

팀 규모와 일정을 고려해 메시지 브로커를 걷어냈지만, 브로커가 해주던 재처리 보장이 사라진다는 걸 알았기 때문에 실패 큐와 재시도 배치를 직접 만들었습니다. 그 구조가 실제로 알림 결함을 잡아냈습니다.

탕탕 · 지갑재판소 (TangTang)

Repository ↗

고정지출을 자동으로 탐지하고, 절약 시뮬레이션과 챌린지로 행동을 유도한 뒤, 월간 리포트로 실제 절감액까지 검증하는 자산관리 서비스. 6인 팀의 팀장으로 7주간 진행하며 실시간 알림과 채팅 인프라, 외부 금융기관 연동, 성능 측정을 담당했습니다.

  • Spring Legacy + MyBatis 기반 모듈러 모놀리스 설계. API 54개 · 테이블 34개 · 라인 커버리지 84.0%
  • 실시간 알림 계층 구현. 초기 설계의 Kafka를 걷어내면서 브로커가 해주던 재처리 보장을 DLQ 테이블과 재시도 배치로 직접 구현
  • 그룹 재판 채팅을 STOMP over WebSocket + Redis로 구현. 번호 발급과 저장이 따로 나가 발생하던 메시지 순서 역전을 Lua 스크립트 원자화로 해결
  • 은행 · 카드 · 대출 · 페이머니 전 업권 금융기관 연동과 CODEF 규격 동일 목 서버 자체 구축
  • k6 부하테스트로 배포 환경 실측. 70 VU까지 효율 95% 선형, 140 VU까지 요청 실패 0%, 병목을 MySQL CPU로 특정
  • 팀장으로 기술 결정 198건을 기록하고 되돌린 결정도 남김
Spring Framework MyBatis MySQL Redis SSE WebSocket/STOMP Vue 3 Docker AWS EC2 k6
